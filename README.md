# news-rag

RAG-ассистент по экономическим и торговым новостям: поиск публикаций и ответы
со ссылками на источники, с учётом дат, атрибуции и существенных оговорок.

Принцип проекта: делаем просто и лаконично. [Правила работы](AGENTS.md).

## Статус

Локальный MVP ищет по Telegram и Trade, отбирает версии на `as_of` и отвечает
по найденным фрагментам через LLM Proxy. Доступны CLI и HTTP API.

```text
Снимки JSONL → индекс версий → отбор по времени → поиск → реранкер
→ поправка на свежесть → контекст → генерация → проверка ссылок
```

Исследование судьи и обучение моделей вынесены в отдельный
[news-rag-research](https://github.com/bruhwalk/news-rag-research).
[Системный дизайн](docs/ml_system_design_doc.md), [архитектура](docs/reference/architecture.md),
[контракт данных](docs/reference/data_contract.md) и [EDA корпуса](eda/README.md)
хранятся в этом репозитории и доступны из Obsidian. Основной документ —
`docs/ml_system_design_doc.md`, дополнительные материалы — `docs/reference/`.
Личные планы и исследовательские заметки ведём в Obsidian, в папке `news-rag-research`.
Исследовательский проект можно разместить рядом или целиком в `research/`;
его подключение к RAG сохраняет одинаковую схему в обоих случаях.

## Данные

Очищенный XLSX: `data/raw/trade_news/relevant_trade_news_202606112005.xlsx`.
Готовый корпус для RAG: `data/processed/trade_news/news.jsonl`.
[Манифест](docs/reference/trade_news_full.json) фиксирует оба пути, SHA256,
количество записей, схему и журнал импорта.
Из файла удалены пустые тексты, полные дубли строк, неоднозначные текстовые
версии и кандидаты на усечение; результаты — в [EDA](eda/README.md).
Большие данные исключены из Git.

Адаптеры источников возвращают JSONL UTF-8 по
[единой схеме новости](schemas/news_document.schema.json):

```json
{
  "id": "web:example.org/news/123",
  "text": "Исходный текст новости",
  "url": "https://example.org/news/123",
  "source": "example.org",
  "published_at": null,
  "language": "ru"
}
```

`id` устойчив для одной публикации. Неизвестные URL, время публикации и язык
оставляем `null`; дополнительные исходные поля можно сохранить в `metadata`.
В Trade JSONL сохраняем исходный календарный день в `metadata.records[].dates`.
При индексации берём самый поздний корректный день среди строк одного URL.
[Правило и сверка с издателями](docs/reference/data_contract.md).
После замены источника повторяем импорт и пересборку индекса.

### Преобразование XLSX

Из корня проекта, в активированном окружении. Импорт обновляет локальную копию
манифеста.

```bash
python -m pip install -r requirements-data.txt
mkdir -p data
cp docs/reference/trade_news_full.json data/trade_news_manifest.json
python -m scripts.import_trade_news --manifest data/trade_news_manifest.json
```

Импортёр проверяет SHA256 входа, сохраняет исходный text и объединяет строки
с одинаковым URI и текстом в одну новость. Международные URL технически
приводятся к ASCII URI: домен — IDNA, кириллица и пробелы — процентное кодирование.
Параметры запроса, фрагмент и готовые escape-последовательности сохраняются.
ID — `web:` и SHA256 полученного URI. Все исходные колонки, кроме text,
сохраняются в `metadata.records`, включая исходный URL, UUID, даты и аннотации.
При противоречивых языковых метках language остаётся null.

Каждая запись проверяется по JSON Schema, включая форматы URL и дат.
Готовый JSONL перечитывается: проверяются уникальность ID/URL, сохранность текста
и всех исходных метаданных. Результат появляется по рабочему пути после проверок.
Журнал `logs/imports/trade_news_full.jsonl` связывает файл, лист и строку XLSX
с ID новости. Параметры `--manifest`, `--output` и `--log` позволяют задать пути явно.
Повторный запуск пересоздаёт производный JSONL и журнал; ID по URL сохраняются.
Если остались `.partial` от прерванного запуска, их нужно проверить перед повтором.

Подготовленный JSONL используется на этапе сборки индекса.

### Разовая выгрузка Telegram

Скрипт [scripts/export_telegram.py](scripts/export_telegram.py) сохраняет тексты
постов и подписи к медиа в JSONL по общему контракту. Медиа и комментарии
не загружаются. Нужен пользовательский аккаунт, бот не подходит.

Установить зависимость в окружение проекта:

```bash
python -m pip install -r requirements-telegram.txt
```

Получить собственные `api_id` и `api_hash` в разделе API development tools
на [my.telegram.org](https://my.telegram.org), затем задать переменные окружения.
В zsh можно ввести значения без сохранения в истории команд:

```zsh
read "TELEGRAM_API_ID?Telegram API ID: "
read -s "TELEGRAM_API_HASH?Telegram API hash: "
export TELEGRAM_API_ID TELEGRAM_API_HASH
```

Пример запуска для выбранных каналов:

```bash
python scripts/export_telegram.py \
  --channels @channel_one @channel_two \
  --since 2026-05-01 \
  --until 2026-11-01 \
  --output data/raw/telegram/2026-05_2026-10.jsonl
```

Каналы передаются как `@username`, `https://t.me/username`, положительный ID
канала или ID с префиксом `-100`. Для числового ID канал должен быть известен
сессии: скрипт сначала загружает список диалогов аккаунта. Если ID неизвестен,
используйте username. Скрипт не вступает в каналы автоматически.

При первом запуске номер телефона, код и пароль 2FA вводятся локально.
Сессия хранится в `.cache/telegram/`, вне Git; для другого аккаунта задайте
другой `--session`. Коды входа и файл сессии не передавайте в чат.

Основной режим — выгрузка за период `[since, until)` по дате публикации в UTC:
нижняя граница включается, верхняя не включается. Без `--until` используется
момент начала выгрузки. Пример выше охватывает шесть полных месяцев.
По умолчанию количественного ограничения нет. `--limit` можно задать для
небольшой пробы: это число просмотренных сообщений **на каждый канал**.
Должно быть задано хотя бы одно из `--since` или `--limit`. При сочетании периода
и лимита скрипт предупреждает о возможном усечении периода. Пустые и служебные
сообщения пропускаются, поэтому текстов может быть меньше просмотренных сообщений.
Данные идут от новых к старым. Повторяющиеся каналы выгружаются один раз.
Существующий файл не перезаписывается; при ошибке остаётся `.jsonl.partial`.
Каждый новый запуск создаёт отдельный срез, без объединения с предыдущими.

В терминале выводятся начало каждого канала, каждые 100 просмотренных сообщений —
число просмотренных/записанных постов и достигнутая дата, затем итог канала.
Файл принудительно сбрасывается на диск вместе с промежуточным прогрессом.
Пока идёт выгрузка, он имеет суффикс .jsonl.partial; после успеха — .jsonl.
За уже работающим старым процессом можно следить во втором терминале через
wc -l и ls -lh для его .partial. Изменение скрипта не обновляет запущенный процесс.
Текущий скрипт не возобновляет незавершённую выгрузку автоматически.

`id` и `source` основаны на числовом ID канала, `published_at` — на времени
публикации Telegram. Язык остаётся `null`, поскольку Telegram его не сообщает.
В metadata сохраняются:

- Канал, ID сообщения, время последней правки и наблюдения.
- Обычные ссылки и ссылки, скрытые за текстом.
- Просмотры, пересылки, число ответов/комментариев и признак секции комментариев.
- Суммы реакций по типам, включая ID custom emoji; API-флаг `reactions_min`.
- Исходный канал, сообщение и дата при доступной атрибуции пересылки.
- Ссылки на сообщение/ветку ответа, ID медиагруппы и тип медиа без загрузки файла.

Неизвестные счётчики остаются `null`, доступный ноль сохраняется как ноль.
`replies_count` — число комментариев, когда `replies_are_comments = true`;
в других случаях это счётчик ответов. Тексты комментариев и списки реагировавших
не загружаются. Эти поля берутся из уже полученного сообщения, без отдельного
API-запроса на каждый пост.

Счётчики относятся к `observed_at`, а не к дате публикации. Сегодняшние просмотры
старого поста нельзя использовать как признак, известный в прошлом. Для основных
опытов по фактической корректности статистика остаётся вне контекста генератора
и судьи; её можно отдельно использовать для отбора, анализа групп и проверки
смещения в пользу популярности. Популярность не служит эталоном истинности.

Это текущие тексты; история прежних редакций
не восстанавливается, дата публикации не доказывает доступность нынешней версии
в прошлом.

Перед выгрузкой для RAG или исследования необходимо подтвердить допустимость
использования выбранных материалов: [условия Telegram](https://telegram.org/tos/content-licensing)
отдельно ограничивают AI/ML-использование. Открытый канал сам по себе не означает
разрешения на такое использование. Это требование уже задано в системном дизайне.

## Запуск MVP

Из корня проекта, в окружении Python 3.12 с SQLite FTS5:

```bash
python -m pip install -e '.[semantic]'
news-rag-index build
news-rag-index embed
python -c 'from news_rag.rag import cross_encoder; cross_encoder()'
news-rag-ask 'Какой была доля платежей в рублях за экспортные поставки в марте 2026 года?' \
  --as-of 2026-11-09T00:26:01+03:00
python -m uvicorn news_rag.api:app --host 127.0.0.1 --port 8000
```

Для сборки нужны оба подготовленных JSONL. Данные и индекс хранятся локально.
Если `data/index/news-mvp-e5.sqlite3` и его векторы E5-small уже собраны,
сразу запускайте запрос или API. По умолчанию используются оба источника,
Hybrid (BM25 и E5-small через RRF), BGE на 20 кандидатах и до 8 целых фрагментов
в контексте. [Принятая конфигурация MVP](docs/reference/architecture.md#принятая-конфигурация-mvp).
Команда Python в примере один раз загружает веса BGE в локальный кэш.

Из Trade берём фрагменты до 1 400 символов, по возможности по границам предложений.
Короткая статья идёт целиком, если также помещается в 512 токенов.
Пост Telegram идёт целиком при том же токенном пределе, иначе делится как Trade.
Предел проверяется для обеих моделей E5 с учётом префикса и служебных токенов.
Если фрагмент всё ещё длиннее, делим его повторно. Индекс сохраняет ID версии,
ссылку и координаты фрагмента в исходном тексте.

[Параметры запуска и примеры команд](docs/reference/cli.md).

`news-rag-ask` выполняет запрос из терминала. HTTP API запускается через
Uvicorn и обслуживает запросы через `POST /ask`. Оба используют один
конвейер ответов. `GET /health` проверяет наличие индекса и настройки клиента.

`POST /ask` принимает `question` и необязательные `as_of` и `period`.
Время указывают в ISO 8601 с часовым поясом. Свежесть учитывается автоматически.

```json
{
  "question": "Что сообщалось о расчётах за экспорт?",
  "as_of": "2026-11-09T12:00:00+03:00",
  "period": {"kind": "publication", "from": "2026-05-01T00:00:00Z", "to": "2026-06-01T00:00:00Z"}
}
```

Для генерации нужен `LLM_PROXY_API_KEY`. Клиент использует переменную окружения
или dotenv: путь из `NEWS_RAG_DOTENV`, иначе `.env` проекта и
`~/.config/llm-proxy/.env`. Модель по умолчанию — `tgpt/t-pro-it-2-1-fp8`;
сравнить другую доступную модель можно через `NEWS_RAG_MODEL`.
Запускайте генерацию только по материалам, которые разрешено передавать в LLM Proxy.
Промпт находится в [answer.md](src/news_rag/prompts/answer.md); ссылки подставляет
приложение из разрешённых фрагментов, а не модель.

### Время и обновления

- `as_of` ограничивает доступность до поиска. Для MVP считаем первый сохранённый
  текст доступным с публикации. Telegram использует точное время, Trade с полем
  `dates` — конец самого позднего указанного дня по Москве. Для последующих
  известных изменений используем время наблюдения. Исторические
  ответы по первому снимку опираются на допущение о неизменности текста.
  Период публикации работает как `[from, to)`. Период события требует уточнения.
- Свежесть автоматически добавляет поправку к рангу с периодом полураспада
  7 дней от `as_of`. При пропуске `as_of` точкой отсчёта служит текущее время.
  Для запросов о свежих новостях дополнительно действуют окно 30 дней и
  предел отставания снимка 48 часов, оба относительно `as_of`. При оценке
  пересылки учитываем дату оригинала. Устаревший снимок даёт отказ.
  Для запроса о текущем курсе валют нужен источник котировок. В новостном
  корпусе можно искать опубликованные значения на заданную дату.
- Для обновления повторно выгружайте согласованные Telegram-каналы с перекрытием
  по датам публикации через существующий `scripts.export_telegram`. Перекрытие
  позволяет заметить правки в этом окне; старые правки вне окна и удаления
  нужны отдельными наблюдениями. Отсутствие поста в новой выгрузке не означает
  удаление. Подтверждённое удаление передаётся записью с тем же ID,
  `metadata.deleted=true` и временем `metadata.observed_at`.
- Собирайте новый индекс с исходными снимками и всеми накопленными файлами
  обновлений: `news-rag-index build --index data/index/news-next.sqlite3
  --telegram-update <новый.jsonl>`. Флаги `--telegram-update` и `--trade-update`
  можно повторять. Постройте векторы для нового индекса и после проверки
  запустите сервис с `NEWS_RAG_INDEX`, указывающим на новый файл. Для рабочего
  режима поставьте выгрузку и сборку в ежедневное расписание среды, где есть
  согласованный доступ к источникам.

Пример ручного обновления (дату начала и список каналов передаёт оператор):

```bash
python -m scripts.export_telegram --channels <согласованные_каналы> \
  --since <начало_окна_UTC> --output data/raw/telegram/update.jsonl
news-rag-index build --index data/index/news-next.sqlite3 \
  --telegram-update data/raw/telegram/update.jsonl
news-rag-index embed --index data/index/news-next.sqlite3
```

### Исследования

В Python `news_rag.rag.RAG.run(Ask(...))` возвращает результат и трассу.
`candidate_ids` или `context_ids` фиксируют пул или точный порядок контекста.
`snapshot_id` проверяет, что ID относятся к нужной сборке. Генератор, реранкер
и промпт можно подменять через Python API. Для повторения прежних экспериментов
режим свежести задаётся в `Ask(..., freshness=...)`. Для точного повтора
архивного запуска используйте тот же SQLite-снимок и векторы. При повторной
сборке индекс получает новый `snapshot_id`.
